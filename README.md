        编写代码：手写代码调用质谱大模型的api，写了一个controller测试，springboot自带的中间件启动。

day2:   编写：1、引入了spring AI依赖，配置对应大模型的url、apiKey等参数，用chatClient对象直接一行代码搞定大模型api的链接
             2、编写 Flux对象接受steam流式响应内容的接口，固定模板+提示词接口，提示词情感分析的接口。
        测试：steam响应的内容会一个一个词打出来，提示词不同返回内容差异很大，会分析提示词的情感状态生成不同倾向的回答。

day3    代码：配置了向量库在内存中，检索向量库，拼接内容，调用大模型分析。
        学习：了解了向量库的概念（向量库把自然语言转化成机器能看懂的数字，并根据提示词把答案范围缩小和提示词一起给到大模型去思考），
             提问AI是不是有一个超大的向量库，反馈他们是通过千亿级别的训练根据已经训练出的经验得出的答案，没有上网查，没有向量库。
             发现AI给出的代码有问题，提问发现错误会不会重新训练，反馈会在一段时间统一训练，当前发现的问题，只在这段对话有效或者
             后续训练修正了，了解到AI也有版本限制，当前版本后发生的事情不知道，除非提供上网查询权限。
        测试：可以根据问题查询出向量库中的答案，没有的会回答不知道。

day4    代码：配置了chatCofig，在内存中存储历史对话（后续要改到redis），调用大模型带上sessionId，让他有记忆功能，优化之前的RAG接口。
        学习：大模型是无状态的，他没有记忆功能，所以要在每次对话时都要带上之前的对话记录。
        测试：提示词提问前面谈话的内容，回答正确，带有记忆。

day5    代码：进行了代码优化，向量库加了缓存减少消耗，优化了检索参数-similarityThreshold（相似度及格线）参数很关键。
        学习：因为只有1个chunk，所以similarityThreshold设置的很低0.3，不然就会把答案筛除掉，后续要优化分成多个chunk；
             没有答案时模型会根据自己的经验乱答，提示词设置了也避免不了，直接代码判空返回，实际生产应该有其他优化方案。
        测试：改后重新测试向量接口读取的缓存文件，功能正常。
